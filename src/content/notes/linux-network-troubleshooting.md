네트워크 문제는 증상이 비슷해도 원인이 여러 계층에 걸쳐 있다. 명령을 무작정 바꾸기보다 **아래 계층부터 하나씩 통과하는지 확인**하면 조사 범위를 빠르게 줄일 수 있다.

## 1. 인터페이스와 주소

먼저 인터페이스가 활성화되어 있고 기대한 IP 주소를 받았는지 확인한다.

```bash
ip -brief link
ip -brief address
```

링크가 `DOWN`이면 케이블·무선 연결·드라이버·가상 인터페이스 설정부터 확인한다. 링크는 올라왔지만 주소가 없다면 DHCP나 정적 주소 설정이 다음 조사 대상이다.

## 2. 라우팅

목적지로 나갈 경로와 실제 선택되는 인터페이스를 확인한다.

```bash
ip route
ip route get 8.8.8.8
```

기본 경로가 없거나 잘못된 게이트웨이를 가리키면 외부 네트워크에 도달할 수 없다. 여러 인터페이스가 있는 장비에서는 metric과 정책 라우팅도 함께 본다.

## 3. IP 도달성

이름 해석을 배제하고 IP 주소로 먼저 시험한다.

```bash
ping -c 3 8.8.8.8
```

단, `ping` 실패가 항상 연결 실패를 뜻하지는 않는다. 방화벽이 ICMP를 차단할 수 있으므로 실제 서비스 포트 검사와 함께 판단한다.

## 4. DNS

IP 통신은 되지만 도메인 접속이 실패하면 리졸버 설정과 DNS 응답을 확인한다.

```bash
resolvectl status
getent hosts example.com
dig example.com
```

`getent`는 시스템의 실제 이름 해석 경로를 따르고, `dig`는 DNS 응답 자체를 자세히 볼 때 유용하다. 둘의 결과가 다르면 `/etc/nsswitch.conf`, 로컬 캐시, 컨테이너별 DNS 설정을 살핀다.

## 5. 포트와 소켓

서버에서는 프로세스가 예상 주소와 포트에서 수신 중인지 확인한다.

```bash
ss -lntup
```

`127.0.0.1`에만 바인딩된 서비스는 외부에서 접근할 수 없다. 클라이언트에서는 TCP 연결 자체가 가능한지 시험한다.

```bash
nc -vz server.example.com 443
curl -v https://server.example.com/health
```

연결 거부는 대개 수신 프로세스가 없거나 방화벽이 명시적으로 거부하는 상황이고, 타임아웃은 경로·방화벽·응답 손실 가능성이 크다.

## 6. 방화벽과 패킷

앞 단계가 정상인데 통신이 되지 않으면 호스트와 네트워크의 필터 규칙을 확인한다.

```bash
sudo nft list ruleset
sudo tcpdump -ni any host 192.0.2.10
```

패킷 캡처에서는 요청이 장비에 들어오는지, 응답이 나가는지부터 본다. 요청 자체가 보이지 않으면 상위 네트워크 경로를, 요청만 보이고 응답이 없으면 로컬 서비스와 방화벽을 조사한다.

## 조사 결과를 남기는 형식

문제를 재현한 시간, 출발지와 목적지, 사용한 프로토콜·포트, 각 단계의 명령 결과를 함께 기록한다. "네트워크가 안 된다"보다 "DNS는 정상이고 TCP SYN이 서버에 도착하지만 443 포트에서 응답이 없다"가 다음 조치를 훨씬 명확하게 만든다.
