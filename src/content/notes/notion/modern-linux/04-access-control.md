# (1) 기본 개요
## 리소스와 소유권
- 리눅스는 다중 사용자 운영체제
- 각 사용자 계정은 실행 파일, 파일, 장치, 기타 리눅스 자산에 접근할 수 있는 사용자 ID와 연결
### 사용자
- 프로세스 실행 및 파일 소유
### 파일
- 소유자 존재 (기본적으로 파일 만든 사용자)
### 프로세스
- 의사소통, 지속성을 위해 파일 사용
- 사용자도 파일 간접적 사용 → 프로세스를 통해야 함

## 샌드 박스
- 어떤 프로그램이나 프로세스를 격리된 환경 안에서 실행해서, 시스템 전체에 영향을 주지 못하게 제한하는 방식

## 접근 제어 유형
- 리눅스는 all-or-nothing 태도 
→ 사용자는 모든걸 변경 가능한 수퍼유지 or 접근 제한된 일반 사용자 중 하나
### 임의 접근 제어(DAC)
- 사용자의 신분을 기반으로 리소스 접근 제한 가능
- 여기서 ‘임의’란, 특정 권한을 가진 사용자가 다른 사용자에게 권한을 전달할 수 있음을 의미
### 강제 접근 제어(MAC)
- 보안 수준을 나타내는 계층 모델 기반
- 사용자에게 허용 등급 할당 → 자신의 허용 등급 이하로 설정된 리소스에만 접근 가능
- 관리자가 모든 권한을 설정 → 엄격, 베타적 접근 제어
- 사용자가 리소스를 소유하여도 권한 스스로 설정 불ㄹ

- SE리눅스
- 리눅스용 강제 접근 제어 구현 모듈
- 정부 기관의 높은 보안 요구사항 충족하도록 개발
- 엄격한 규칙 → 사용 어려움
- 또 다른 옵션으로 버전 2.6.36부터 리눅스 커널에 포함된 AppArmor도 존재

# (2) 사용자
- 리눅스에서 목적/의도적인 사용 관점에서 사용자 계정을 2개로 구별
### 시스템 사용자(시스템 계정)
- 일반적으로 프로그램(=daemon)은 해당 유형의 계정으로 백그라운드 프로세스 실행
- 이 프로그램은 네트워킹 같은 운영체제 일부 or 애플리케이션 계층에도 존재 가능
### 일반 사용자
- 셸을 통해 리눅스를 대화식으로 사용하는 인간 사용자 유형

- 리눅스는 UID(사용자ID)를 통해 사용자 식별
- 사용자는 GID(그룹ID)를 통해 식별되는 하나 이상의 그룹에 속함
- 일반적으로 root라 부르는 수퍼유저는 제한이 전혀 적용 X 
→ root는 권한이 너무 많으므로 해당 사용자로 작업하는 건 피해야 함 (시스템 파괴 가능)
### UID 규칙
- UID 0: root 사용자
- UID1 \~ 999: 시스템 사용자에게 지정
- UID 65534: nobody 사용자, 원격 사용자를 잘 알려진 ID에 매핑하는 데 사용
- UID1000 \~ 65533, 65536 \~ 4294967294: 일반 사용자
- 자신의 UID는 `$ id -u` 명령어로 파악 가능

# (3) 권한
## 파일 권한
- ‘리소스에 접근’한다는 리눅스 개념의 핵심 (리눅스에서 모든 것은 파일)
### 권한
- 사용자: 파일의 소유자
- 그룹 : 하나 이상의 구성원을 가짐
- 나머지 : 그 밖의 모두
### 접근 유형
- 읽기(r)
- 일반 파일 → 사용자가 파일 내용 볼 수 있음
- 디렉터리 → 사용자가 디렉터리에 있는 파일 이름 확인 가능
- 쓰기(w)
- 일반 파일 → 사용자가 수정 및 삭제 가능
- 디렉터리 → 사용자가 디렉터리에서 파일 생성, 이름 변경, 삭제 가능
- 실행(x)
- 일반 파일 → 읽기 권한도 있을 경우 파일 실행 가능
- 디렉터리 →  사용자가 파일 정보 접근할 수 있도록 허용 (=cd, ls 가능하도록

## 프로세스 권한
### 런타임 권한 관련 사용자 ID
- RUID(Real User ID)
- 프로세스를 실제로 시작한 사용자의 UID
- 프로세스의 실제 소유자를 나타냄
- `getuid(2)`를 통해 확인 가능
- EUID(Effective User ID)
- 커널이 프로세스의 권한을 판단할 때 주로 사용하는 UID
- setuid 프로그램 실행 시 RUID와 달라질 수 있음
- `geteuid(2)`를 통해 확인 가능
- Saved Set-User-ID
- 프로세스가 이전 유효 UID를 저장해 두는 값
- setuid 프로그램에서 권한을 일시적으로 낮췄다가 다시 회복할 때 사용됨
- FSUID(Filesystem UID)
- 리눅스에서 파일 시스템 접근 권한을 검사할 때 사용하는 UID
- 일반적으로 EUID와 같은 값으로 유지됨

- 프로세스 UID는 다음과 같은 여러 용도로 사용됨
- 파일 접근 권한
- 신호 전송 위한 권한 설정
- 스케줄링, 우선순위에 대한 권한 처리
- 리소스 제한 확인

# (4) 고급 권한 관리
## 캐퍼빌리티
- 전통 모델에서는 일반 사용자 or root 권한 중 하나 였음
- root 권한이 너무 강력해서 기능별로 쪼갠 것
- 일반적으로 시스템 수준의 작업에만 관련 (대부분의 경우 캐퍼빌리티에 의존 필요 X)

## seccomp 프로필
- secure computing mode
- 프로세스가 사용할 수 있는 시스템 콜을 제한하는 기능

## 접근 제어 목록(ACL)
- ACL은 기본 소유자/그룹/기타 사용자 권한보다 더 세밀하게 파일 권한을 설정하는 기능<br>
# (5) 우수 사례
- 최소 권한 원칙 : 모슨 사람/프로세스는 주어진 작업을 수행하는데 필요한 권한만 가질 것
- setuid를 피할 것 : 공격자에 취약하므로, 대신 캐퍼빌리티 활용
- 감사(auditing) : 모든 작업들을 변조 불가능 한 방법으로 결과 로그에 기록
# (6) 정리
- 리눅스에서 작업 시, 사용자/프로세스/파일 간의 관계를 기억해야 함
