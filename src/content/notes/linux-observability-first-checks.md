관측가능성은 도구를 많이 설치하는 일이 아니라 **외부 신호로 내부 상태를 설명할 수 있게 만드는 것**이다. 시스템이 느릴 때는 바로 튜닝하기보다 기준 상태와 현재 상태를 비교하며 가설을 좁힌다.

## 전체 상태를 빠르게 훑기

```bash
uptime
free -h
vmstat 1
```

`uptime`의 load average는 CPU 사용률이 아니라 실행 중이거나 실행을 기다리는 작업의 평균에 가깝다. 코어 수, I/O 대기, 작업 특성과 함께 해석해야 한다.

`free`에서 `free` 값이 작다는 이유만으로 메모리 부족이라고 판단하지 않는다. Linux는 남는 메모리를 캐시로 활용하므로 `available`, swap 사용 추세, 회수 지연을 함께 본다.

## CPU

```bash
top
pidstat -u 1
```

확인할 내용은 단순 사용률보다 구체적이다.

- 특정 프로세스나 스레드에 사용량이 집중되는가
- 사용자 시간과 커널 시간 중 어느 쪽이 증가했는가
- I/O 대기 시간이 높은가
- 실행 큐가 코어 수에 비해 계속 긴가

짧은 순간의 스파이크와 지속적인 포화는 대응이 다르므로 시간 흐름을 함께 기록한다.

## 메모리

```bash
vmstat 1
pidstat -r 1
```

swap 입출력이 지속되고 응답 시간이 함께 나빠진다면 메모리 압박을 의심할 수 있다. 프로세스의 RSS가 계속 증가하는지, 페이지 폴트가 급증하는지도 확인한다. OOM이 발생했다면 커널 로그를 살핀다.

```bash
journalctl -k --since "30 minutes ago" | grep -i -E "oom|killed process"
```

## 디스크 I/O

```bash
iostat -xz 1
pidstat -d 1
```

장치 사용률 하나만 보지 말고 요청 지연, 큐 길이, 처리량을 함께 본다. 디스크가 바쁜데 어떤 프로세스가 원인인지 보이지 않으면 프로세스별 I/O로 연결한다.

## 네트워크

```bash
ss -s
ss -lntup
ip -s link
```

재전송, 드롭, 오류 카운터, 연결 상태의 비정상적 증가를 확인한다. 애플리케이션 지연이 네트워크 때문인지 판단하려면 서버 처리 시간과 클라이언트가 본 전체 시간을 분리해서 측정하는 것이 좋다.

## 로그·지표·추적의 역할

- 로그: 특정 시점에 어떤 사건이 발생했는지 설명한다.
- 지표: 값이 시간에 따라 어떻게 변했는지 보여준다.
- 추적: 요청이나 실행 흐름이 어디에서 시간을 소비했는지 연결한다.

지표로 이상 구간을 찾고, 로그로 사건을 확인한 뒤, 필요한 경우 추적으로 병목 위치를 좁히는 순서가 효율적이다.

## 변경 전후를 비교한다

관측 없이 리소스를 늘리면 원인이 해결됐는지 알 수 없다. 한 번에 하나의 조건만 바꾸고 같은 부하에서 다시 측정한다.

1. 증상과 재현 조건을 기록한다.
2. CPU·메모리·I/O·네트워크 중 병목 후보를 정한다.
3. 후보를 확인할 지표를 선택한다.
4. 설정이나 리소스를 하나만 변경한다.
5. 같은 조건에서 결과를 비교한다.

좋은 대시보드는 모든 숫자를 모은 화면이 아니라, 장애 가설을 빠르게 기각하거나 채택할 수 있게 해주는 화면이다.
