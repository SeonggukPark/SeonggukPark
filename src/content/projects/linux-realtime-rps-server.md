## 프로젝트 개요

운영체제 과목에서 Linux 환경의 2인용 실시간 가위바위보 게임을 C로 구현했습니다. 서버 한 대와 클라이언트 두 대가 TCP로 연결되며, 각 사용자가 `R`, `S`, `P` 중 하나를 입력하면 서버가 두 입력을 모아 승패를 판정하고 `win`, `lose`, `draw` 결과를 반환합니다.

Socket API, pthread, mutex와 System V 메시지 큐를 하나의 실행 흐름으로 결합했습니다. 네트워크 통신을 담당하는 스레드와 게임 판정을 담당하는 스레드를 분리하고 메시지 큐로 연결해, 운영체제에서 배운 네트워크·동시성·IPC 개념을 실제 프로그램으로 구현했습니다.

## 담당 역할

- C 기반 Linux 클라이언트·서버 프로그램과 게임 진행 로직 구현
- Socket API를 이용한 두 클라이언트의 연결, 입력 수신과 결과 송신 처리
- 클라이언트별 `serverthread`와 판정 전용 `evalthread` 구성
- 공유 접속 카운터 `visits`를 보호하는 mutex 임계 구역 적용
- 두 개의 System V 메시지 큐를 이용한 스레드 간 입력·결과 전달
- Ubuntu 22.04.2 LTS 환경에서 정상·실패 시나리오 실행 검증

## 시스템 구성

1. 서버가 기본 TCP 포트 `5193`에 소켓을 생성하고 `bind()`·`listen()` 후 접속을 기다립니다.
2. 서버 시작 시 게임 판정을 담당하는 `evalthread`를 생성하고 키 `1234`, `1235`의 메시지 큐 두 개에 연결합니다.
3. `accept()`가 클라이언트 연결을 수락할 때마다 해당 소켓을 담당하는 `serverthread`를 생성합니다.
4. 각 `serverthread`는 클라이언트 입력을 자신의 메시지 큐로 전달한 뒤 판정 결과를 기다립니다.
5. `evalthread`는 두 큐에서 입력을 하나씩 수신하고 `evalgame()`으로 승패를 계산한 뒤 각 큐에 결과를 돌려보냅니다.
6. `serverthread`가 결과를 TCP 소켓으로 해당 클라이언트에 전송하고 다음 라운드를 반복합니다.

## 핵심 구현

### Socket 기반 실시간 통신

- `socket(PF_INET, SOCK_STREAM, ...)`으로 TCP 소켓 생성
- 서버의 `bind()`·`listen()`·`accept()`와 클라이언트의 `connect()` 흐름 구현
- `send()`·`recv()`를 이용해 선택값과 게임 결과를 양방향으로 전달
- 명령행 인자로 호스트와 포트를 지정하고, 생략 시 `localhost:5193` 사용

### pthread 기반 병렬 처리

- 클라이언트마다 하나의 `serverthread`를 생성해 연결과 입력을 독립적으로 처리
- 별도의 `evalthread`가 네트워크 처리에서 게임 판정 책임을 분리
- 공유 변수 `visits`의 증가 구간을 `pthread_mutex_lock()`과 `pthread_mutex_unlock()`으로 보호
- 잠금 범위를 접속 카운터 갱신으로 제한해 소켓 입출력 전체가 직렬화되지 않도록 구성

### System V Message Queue 기반 전달

- `msgget()`으로 두 메시지 큐를 생성하고 각 클라이언트 스레드와 1:1로 연결
- `msgsnd()`·`msgrcv()`로 `serverthread`와 `evalthread` 사이의 입력·결과 전달
- 첫 번째 큐는 Client A, 두 번째 큐는 Client B의 통신 채널로 사용
- 종료 요청 시 `msgctl(..., IPC_RMID, ...)`로 해당 메시지 큐 제거

### 게임 판정

- `evalgame(char a, char b)`가 두 사용자의 선택을 비교해 무승부 `0`, A 승리 `1`, B 승리 `2` 반환
- 판정값을 각 클라이언트 관점의 `win`, `lose`, `draw` 문자열로 변환
- 한 라운드가 끝나면 같은 연결을 유지한 채 다음 입력을 받아 반복 대전

## 실행 검증

Ubuntu 22.04.2 LTS에서 서버와 두 클라이언트를 각각 실행해 다음 흐름을 확인했습니다.

- 서버 시작 후 판정 스레드와 두 메시지 큐가 정상 생성되는지 확인
- Client A와 B가 차례로 접속하고 서버가 각 연결에 통신 스레드를 생성하는지 확인
- A의 입력이 먼저 대기하고 B의 입력이 도착하면 두 결과가 각 클라이언트에 반환되는지 확인
- `R`, `S`, `P` 조합을 바꾸며 승리·패배·무승부 판정과 반복 라운드 동작 확인
- 서버보다 클라이언트를 먼저 실행했을 때 연결 실패가 처리되는지 확인

## 확인한 제약과 개선 방향

보고서의 실행 실험을 통해 정상 동작뿐 아니라 초기 구현의 한계도 함께 확인했습니다.

- `evalthread`가 A 큐를 먼저 기다리는 구조여서 Client A가 B보다 먼저 입력해야 합니다. 두 입력을 순서와 무관하게 처리하려면 조건 변수나 `poll()` 계열의 대기 구조가 필요합니다.
- 두 개의 고정 메시지 큐와 `visits` 값으로 사용자를 구분해 세 번째 접속과 재접속을 처리하기 어렵습니다. 연결별 세션 객체와 명시적인 사용자 슬롯 관리가 필요합니다.
- 한 사용자가 종료했을 때 남은 사용자의 라운드를 정리하고 새로운 사용자를 받을 수 있는 세션 복구 로직이 부족합니다.
- 서버 종료 직후 재실행하면 `bind failed`가 발생할 수 있어 소켓 종료 처리와 `SO_REUSEADDR` 설정을 보완할 필요가 있습니다.
- `Q` 종료 흐름은 클라이언트·통신 스레드·판정 스레드와 메시지 큐를 함께 정리하도록 개선할 수 있습니다.

## 결과

- 두 클라이언트가 동시에 접속해 여러 라운드의 가위바위보 게임을 진행하는 TCP 서버를 완성했습니다.
- 클라이언트별 통신 스레드, 판정 스레드와 메시지 큐의 역할을 분리해 전체 동작 흐름을 설계했습니다.
- mutex로 공유 상태의 임계 구역을 보호하며 멀티스레드 서버의 동기화 방식을 적용했습니다.
- 성공 시나리오와 연결·종료 실패 시나리오를 함께 시험하고, 후속 개선이 필요한 세션 수명주기와 입력 순서 의존성을 구체적으로 정리했습니다.
